# امنیت و حریم خصوصی — Security notes

این سند می‌گوید سامانه از چه چیزی محافظت می‌کند، با چه سازوکاری، و **چه چیزی را پوشش نمی‌دهد**.
هر ادعای زیر یا با تست خودکار پوشش داده شده (نام تست در پرانتز) یا صریحاً «بدون تست» علامت خورده است.

## داده‌ی حساس و محافظت آن

| داده | نحوه‌ی ذخیره | تست |
|---|---|---|
| کد ملی، تاریخ تولد، موبایل، نام زائر | رمزشده با AES‑256‑GCM، با نانس تصادفی و «زمینه‌ی ستون» (متن رمزشده‌ی یک ستون در ستون دیگر باز نمی‌شود) | `TestSealOpen`, `TestPersonalDataIsEncryptedAtRest` |
| جست‌وجو با کد ملی/موبایل | شاخص کور HMAC‑SHA256 (بدون رمزگشایی) | `TestBlindIndex`, `TestPersonalDataIsEncryptedAtRest` |
| رمز عبور خادمان | argon2id (۶۴ مگابایت، salt تصادفی) | `TestPasswords` |
| توکن‌های نشست | فقط هش SHA‑256 در Redis؛ توکن خام ذخیره نمی‌شود | `TestTokens`, `TestLoginLockoutAndTokens` |
| نمایش در API | کد ملی و موبایل همیشه ماسک‌شده (`008****948`) | `TestEndToEndOverHTTP` |
| لاگ | ساختاریافته؛ هرگز query string، بدنه یا هدر ثبت نمی‌شود؛ جست‌وجوی زائر با POST است تا کد ملی در URL نیاید | `scripts/smoke.sh` (بررسی نبودن کد ملی/رمز/توکن در لاگ) |
| تصویر کارت ملی | **ذخیره نمی‌شود** (سامانه اصلاً تصویر دریافت نمی‌کند) | — |
| پاک‌سازی | زائری که چادر در اختیار ندارد و `RETENTION_DAYS` روز دیده نشده، ناشناس می‌شود (داده‌ی شخصی پاک، آمار می‌ماند) | `TestRetentionAndReminders` |

### کلیدها
- `PII_ENC_KEY` (رمزنگاری) و `PII_IDX_KEY` (شاخص) **باید متفاوت** باشند؛ برنامه در غیر این صورت بالا نمی‌آید.
- کلیدها از فایل (Docker secrets) خوانده می‌شوند، نه از image یا مخزن.
- **اگر کلیدها گم شوند، داده‌ی رمزشده برای همیشه از دست می‌رود.** نسخه‌ی پشتیبان کلید را جدا از سرور نگه دارید.
- **محدودیت شناخته‌شده:** ابزار چرخش کلید (re‑encrypt) هنوز نوشته نشده. اگر کلید لو رفت، باید اسکریپت جداگانه نوشت. (بدون تست)

## احراز هویت و دسترسی

- ورود با شناسه‌ی شخصی؛ حساب مشترک وجود ندارد. رمز موقت فقط اجازه‌ی تغییر رمز می‌دهد (`TestEndToEndOverHTTP`).
- قفل بعد از ۵ تلاش ناموفق برای هر شناسه، ۱۵ دقیقه (`TestLoginLockoutAndTokens`). قفل جداگانه‌ی هر IP (۳۰ تلاش ناموفق) و محدودیت ۱۲۰ ورود در دقیقه برای هر IP پیاده شده ولی **تست مستقل ندارد**؛ سقف IP عمداً بالاست چون چند ده خادم پشت یک روتر گیت وارد می‌شوند.
- پیام خطا برای «شناسه‌ی ناموجود» و «رمز غلط» یکسان است (`TestEndToEndOverHTTP`). برای نزدیک‌کردن زمان پاسخ، برای شناسه‌ی ناموجود هم یک هش argon2 ساختگی بررسی می‌شود؛ **این زمان‌ها اندازه‌گیری نشده‌اند**.
- توکن دسترسی ۱۵ دقیقه؛ توکن تازه‌سازی یک‌بارمصرف و چرخشی (`TestLoginLockoutAndTokens`).
- غیرفعال‌کردن کاربر، تغییر نقش یا تغییر رمز، **همه‌ی نشست‌ها را فوراً** باطل می‌کند.
- ۷ نقش با حداقل دسترسی؛ فقط `admin` کاربر و چادر و تنظیمات را مدیریت می‌کند (`TestPermissions`).
- هر نقش فقط در مکان‌های مجاز شیفت شروع می‌کند (کارگاه نمی‌تواند در گیت ثبت کند) (`TestShiftAndPermissionGuards`).
- درخواست‌های آفلاین به شیفتِ **همان کاربر** نسبت داده می‌شوند؛ شیفت دیگران پذیرفته نمی‌شود (`TestSyncOfflineQueue`).
- جدول وضعیت‌ها در `domain/status.go` تعیین می‌کند چه نقشی چه تغییری می‌دهد؛ مثلاً کارگر کارگاه نمی‌تواند کار خودش را تأیید کند (`TestTransitions`).

## یکپارچگی داده و ردپا

- **یک چادر، یک تخصیص فعال:** با `UPDATE ... WHERE status='ready'` و همچنین ایندکس یکتای جزئی در Postgres. حتی اگر منطق Go اشتباه شود، دیتابیس جلوی تخصیص دوباره را می‌گیرد (آزمایش جهش انجام شد؛ `TestOnlyOneWinner...`).
- **تکرار امن (idempotency):** هر عملیات `op_id` دارد؛ ارسال دوباره همان نتیجه را برمی‌گرداند و پیامک/ثبت تکراری نمی‌سازد (`TestIdempotentReplay`, `TestSyncOfflineQueue`).
- **لاگ فقط‌افزودنی:** `audit_log` و `tent_events` با تریگر **و** با محدودکردن دسترسی نقش اجرا (REVOKE) محافظت شده‌اند. نقش اجرا نمی‌تواند تریگر را حذف یا جدول بسازد (`TestAppendOnlyTables`, `TestRuntimeRoleCannotTamper`).
- دو نقش دیتابیس: `chador_owner` (فقط مایگریشن) و `chador_app` (فقط DML). سرویس هیچ‌وقت با نقش مالک اجرا نمی‌شود.

## شبکه و کانتینر (پیکربندی `deploy/`)

- فقط Caddy پورت عمومی دارد. شبکه‌ی `data` (Postgres/Redis) و `app` **internal** هستند، یعنی راه خروج به اینترنت ندارند.
- API و worker فقط از شبکه‌ی `egress` به سرویس استعلام/پیامک وصل می‌شوند.
- image نهایی بدون shell، با کاربر غیر root، فایل‌سیستم فقط‌خواندنی، `cap_drop: ALL`، `no-new-privileges`.
- Redis با رمز؛ Postgres با `scram-sha-256` و checksum داده.
- محدودیت: کانتینر Redis با کاربر root داخل کانتینر (همه‌ی capabilityها حذف) اجرا می‌شود و رمزش در لیست پردازش‌ها برای root میزبان دیده می‌شود. برای سخت‌تر کردن: `user: redis` و فایل پیکربندی (روی Docker واقعی آزموده شود).
- هدرها: HSTS، CSP، `nosniff`، `no-store` روی پاسخ‌های API، `X-Frame-Options: DENY` (`TestEndToEndOverHTTP`).
- محدودیت: بدنه‌ی درخواست ۱ مگابایت (۲ برای sync)، ۶۰ درخواست در ثانیه برای هر نشست، timeout ده‌ثانیه‌ای.
- **بدون تست در این محیط:** ساخت واقعی image، اجرای compose، و صدور گواهی TLS. فایل‌ها با `docker compose config` اعتبارسنجی شده‌اند ولی روی یک daemon واقعی اجرا نشده‌اند (daemon در محیط توسعه در دسترس نبود). قبل از استفاده‌ی واقعی `make up` را روی سرور آزمایشی اجرا کنید.

## آنچه این سامانه پوشش **نمی‌دهد**

- امنیت فیزیکی و خود گوشی‌ها: اگر گوشی خادم با توکن فعال دزدیده شود تا ۱۵ دقیقه (یا تا خروج) معتبر است. خروج از حساب و غیرفعال‌سازی راه کنترل است.
- امنیت سرویس‌های بیرونی (استعلام و پیامک) و قرارداد آن‌ها.
- امنیت وب‌اپ PWA (CSP و ذخیره‌ی توکن در مرورگر کار تیم front-end است؛ پیشنهاد: توکن در حافظه، نه localStorage).
- پشتیبان‌گیری خارج از سرور؛ `backup.sh` فایل می‌سازد ولی جابه‌جایی آن به محل امن با شماست.
- تست نفوذ مستقل انجام نشده است. پیش از استفاده‌ی عمومی توصیه می‌شود.
- مقررات قانونی نگه‌داری داده‌ی هویتی: باید با مرجع حقوقی مجموعه تأیید شود؛ این سند مشاوره‌ی حقوقی نیست.
